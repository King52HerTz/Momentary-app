# 开发流程与提交规范

## 1. 仓库边界

### Android GitHub 仓库

允许提交：

- `app/` Android 代码与测试；
- Gradle 配置；
- Android README；
- 产品、客户端架构、UI 和共享 API 契约文档。

禁止提交：

- `backend/` 后端代码与内部文档；
- `.env`、API Key、签名文件和凭据；
- 原始参考图片与私人设计材料；
- APK、构建目录、截图产物和本机配置。

后端未来需要版本控制时，创建单独私有仓库，不放回 Android 仓库。

## 2. 开始任务前

1. 确认任务属于当前里程碑；
2. 阅读产品计划、相关技术方案和 API 契约；
3. 写出可观察的验收条件；
4. 检查工作区，保留用户已有修改；
5. 涉及 API 时先修改契约，再写两端代码；
6. 涉及数据结构时先设计 migration 和回滚策略。

## 3. 功能开发顺序

```text
Domain model
  -> pure business logic
  -> unit tests
  -> repository/data source
  -> integration tests
  -> ViewModel state
  -> Compose UI
  -> UI test / emulator verification
  -> docs status update
  -> commit and push
```

UI 不得成为业务规则的第一落点。

## 4. 提交粒度

一个提交只表达一个目的，并保持可构建：

```text
docs: establish project architecture and delivery roadmap
feat(data): establish room persistence schema
feat(data): migrate legacy local records to room
refactor(chat): isolate chat view model and repository
feat(diary): persist source-backed diary drafts
test(diary): cover generation retry and idempotency
fix(export): prevent long journal image clipping
```

禁止：

- “update code”“继续开发”这类无语义提交；
- 一个提交同时改数据层、全套 UI 和无关样式；
- 测试失败时先提交再说；
- 为了干净历史而覆盖用户未提交的改动。

## 5. 每项功能完成定义

只有同时满足以下条件才可以标为完成：

- 行为符合产品与 API 文档；
- 成功、空状态、加载、失败和重试均处理；
- 原始用户内容不会因失败丢失；
- 领域逻辑有自动化测试；
- 关键 UI 在模拟器验证；
- `testDebugUnitTest`、`assembleDebug`、`lintDebug` 通过；
- 没有 API Key、正文日志或本机文件进入暂存区；
- 文档完成度和下一任务已更新；
- 创建单一功能提交并推送 GitHub。

## 6. API 变更流程

1. 修改 `docs/API契约-v1.md`；
2. 后端添加或更新契约测试；
3. 后端实现并在本机验证；
4. Android 添加 DTO 和 MockWebServer 测试；
5. Android 接入 UI；
6. 运行端到端联调；
7. 删除旧接口，不长期维护 v0/v1 双实现。

破坏性变更必须升级 API 版本，不允许悄悄改字段含义。

## 7. 数据库变更流程

- 每次 schema 变化增加版本；
- 提供 migration，不使用 destructive migration；
- 导出 Room schema；
- 用旧 schema 样本跑 migration test；
- 验证升级后记录数量、来源关系和正文不变；
- 删除字段前至少经历一个兼容版本。

## 8. 测试矩阵

| 改动 | 必须测试 |
| --- | --- |
| 纯领域逻辑 | JUnit 单元测试 |
| Coroutine/ViewModel | coroutines-test |
| Room/迁移 | Room instrumentation test |
| HTTP DTO | MockWebServer + serialization test |
| Compose 交互 | Compose UI test |
| 导出图片 | 模拟器截图 + 像素/尺寸检查 |
| 完整里程碑 | 真实本机后端端到端流程 |

## 9. 安全检查

提交前执行：

- `git diff --cached --name-only`，确认不含 `backend/`、`.env`、图片素材和构建产物；
- 搜索 `AI_API_KEY`、`Authorization: Bearer`、`sk-` 等凭据模式；
- 确认日志不包含片刻、日记或对话正文；
- Release Base URL 使用 HTTPS；
- 错误界面不展示服务端堆栈和供应商原始响应。

## 10. 文档维护

- `产品计划书` 只描述需求和边界；
- `项目现状审计` 记录已知事实与技术债；
- `Android 技术方案` 描述客户端怎么实现；
- `API 契约` 描述双方交换什么；
- `下一阶段开发计划` 描述何时做和如何验收；
- `UI 重设计规范` 描述视觉规则；
- 后端内部实现只写在本机后端文档。

同一规则不在多份文档重复维护；需要引用时使用链接。
